# EvidenceMeet — Project Contract

> **Version:** 1.0  
> **Date:** 2026-09-22  
> **Status:** Active  

---

## 1. Project Purpose

EvidenceMeet is an **evidence-based meeting summarization system**. It processes raw meeting audio into structured transcripts and then generates intelligence outputs (summaries, claims, action items, etc.) that are **traceable back to the original transcript evidence**.

The system is split into two independent member pipelines that communicate through a well-defined shared JSON interface.

---

## 2. Definition of "Evidence-Based"

"Evidence-based" means that every important piece of information generated by the intelligence layer **must be traceable to supporting evidence in the original meeting transcript**. Specifically, a piece of evidence includes:

| Evidence Attribute | Description |
|---|---|
| `segment_id` | Which transcript segment supports the claim |
| `speaker` | Who said it |
| `start` / `end` | When it was said (timestamps in seconds) |
| `quote` | The supporting text from the transcript |

> **[PLANNED]** The evidence object structure above is a design goal. It is **not yet implemented** in any code.

## 5. Data Flow Between Members

### 5.1 Current Data Flow

```
Member 1 writes JSON → data/mock_transcripts/{filename}_transcript.json
Member 2 reads JSON  → consumes the segments for preprocessing and summarization
```

### 5.2 Current Data Flow in Streamlit (`app/app.py`)

In the Streamlit app, the flow is **in-memory** (no file I/O between members):

1. `transcribe_audio()` → `raw_text`, `segments`, `language`
2. `diarize_audio()` → `diarization_intervals`
3. `align_and_merge(segments, diarization_intervals)` → `aligned_transcript`
4. `clean_transcript(raw_text)` → `cleaned_text`
5. `generate_summary(cleaned_text)` → `summary_text`

> **IMPORTANT DISCREPANCY:** In the Streamlit app, Member 2's `clean_transcript()` and `generate_summary()` currently operate on the **raw full text** from Whisper (`raw_text`), **not** on the structured per-segment JSON. The preprocessing is not applied per-segment. See Section 8 for details.

## 6. Baseline vs. Proposed Evidence-Grounded System

### Baseline (CURRENT)

| Aspect | Status |
|---|---|
| Input to Member 2 | Flat concatenated text from Whisper (`raw_text`) |
| Preprocessing | Filler removal on the full text |
| Summarization | BART map-reduce on cleaned full text |
| Output | Plain text summary |
| Evidence tracing | **None** — no link back to speakers, timestamps, or segments |

### Proposed Evidence-Grounded System (PLANNED)

| Aspect | Goal |
|---|---|
| Input to Member 2 | Structured JSON with per-segment speaker/timestamp data |
| Preprocessing | Per-segment cleaning preserving segment boundaries |
| Intelligence outputs | Claims, decisions, action items — each with evidence objects |
| Evidence tracing | Every output links to `segment_id`, `speaker`, `start`/`end`, `quote` |
| Summary | Evidence-grounded summary where every claim is backed by transcript evidence |
| Contradiction detection | Identifies conflicting statements across speakers with supporting evidence |

> **The baseline BART summarizer must be preserved** as a reference/fallback throughout development.

## 7. Rules for Changing the Shared Interface

1. **The shared JSON schema** (documented in `MEMBER1_INTERFACE.md`) is the contract between Member 1 and Member 2.
2. **No field may be removed or renamed** without both members' agreement and a contract version bump.
3. **New fields may be added** as long as they are **optional** (Member 2 must tolerate their absence in older transcripts).
4. **All schema changes** must be documented in `docs/CHANGELOG.md` with a date and rationale.
5. **The `cleaned_text` field** is currently a blank placeholder (`""`). Its semantics must be agreed upon before either member populates it.
6. **The `overlap` field** is currently hardcoded to `false`. Its semantics must be agreed upon before it is activated.

## 8. Discrepancies Discovered

The following discrepancies between the intended architecture and the actual code have been identified during this audit:

| # | Discrepancy | Details |
|---|---|---|
| 1 | **Member 2 does not consume the structured JSON** | In `app.py`, `clean_transcript()` receives `raw_text` (the full concatenated Whisper output), not the per-segment transcript JSON. The structured JSON with speakers and timestamps is effectively unused by Member 2. |
| 2 | **`cleaned_text` field is always empty** | `main.py` sets `"cleaned_text": ""` as a placeholder. It is never populated by Member 1 or Member 2. The intent (who fills it, when) is undefined. |
| 3 | **`overlap` field is always `false`** | `main.py` hardcodes `"overlap": False`. No overlap detection logic exists anywhere. |
| 4 | **`raw_text` vs `text` are identical** | In `main.py`, both `raw_text` and `text` are set to `block["text"]` (the aligner output). They are currently always equal. The intended distinction is not implemented. |
| 5 | **`pipeline.py` files are empty** | Both `member1_speech/pipeline.py` and `member2_intelligence/pipeline.py` exist but are empty (0 bytes). |
| 6 | **Speaker labels are opaque** | PyAnnote assigns labels like `SPEAKER_00`, `SPEAKER_04`. These are arbitrary and not consistent across runs or files. No speaker name resolution exists. |

## 9. Design Principles

1. **Evidence First:** Every intelligence output must be traceable to transcript evidence. No unsupported claims.
2. **Preserve the Baseline:** The BART summarizer is the established baseline. It must remain available and functional even as new intelligence components are added.
3. **Clean Interface Boundaries:** Member 1 and Member 2 communicate exclusively through the shared JSON schema. Neither member should reach into the other's internals.
4. **Additive Schema Evolution:** The shared JSON schema evolves by adding optional fields, never by removing or renaming existing ones.
5. **Segment Integrity:** Transcript segments with their speaker and timestamp data are the atomic units of evidence. They must not be merged or destroyed by the intelligence pipeline.
6. **Reproducibility:** Given the same audio input and model versions, the pipeline should produce deterministic, reproducible output.
7. **Separation of Concerns:** Speech processing (Member 1) and intelligence/NLP (Member 2) remain independent modules with no cross-dependencies beyond the shared interface.
